# Parent performance finding — Moonlit Courier v1.1 renderer

Date: 2026-10-24 (parent measurement, read-only on the writer's candidate)
Status: **nonblocking for correctness; blocks nothing already verified. Must be fixed or explicitly accepted before v1.1 ships.**

## What was measured

Instrumented `MCRenderer.draw` + `requestAnimationFrame` + `matchMedia` before app bootstrap, fake
clock identical to the suite, real wall-clock time per 240 simulation ticks (2 s of game time),
1366×768 DPR2 unless noted.

| Build | real ms / 240 ticks | notes |
|---|---|---|
| v1.0 baseline (`de7e75f`) | ~4 700 | 1 backdrop blit/frame |
| v1.1 candidate (`b8e92c9`) | ~9 550 | 4 backdrop blits/frame |
| v1.1, effects loop disabled | ~9 500 | not the cause |
| v1.1, ambient sparkle loop disabled | ~9 690 | not the cause |
| v1.1, only plane 0 drawn | ~4 870 | **cause isolated** |
| v1.1, 3 planes (sky merged into far) | ~8 000 | helps, not enough |
| v1.1, planes drawn with explicit 2048×540 dest | ~9 540 | not stride/filter |
| v1.1, planes cached at device resolution | ~4 420 | **fix works, but see memory** |
| v1.1, hoisted `matchMedia` only | ~9 530 | not the cause |

Wall-clock frames per second in the same browser, real clock: v1.0 ~26 fps vs v1.1 ~13 fps at
1366×768 DPR2; ~26 vs ~17 at 390×844 DPR2.

## Cause

v1.1 draws **four full-viewport `drawImage` blits per frame** (sky/far/mid/near parallax planes) where
v1.0 drew one. In this software-rasterized headless Chromium the cost scales with destination pixels
painted per frame, so the art upgrade roughly doubles frame cost. It is fill-rate, not JavaScript:
`draw`, `stepGame`, `snapshot` and `observe` together measure under 0.5 ms, while the same 240 ticks
take ~40 ms of wall clock.

The per-frame `root.matchMedia('(max-width:600px)')` in `draw()` is a separate real (if smaller)
defect: it increments a style-recalculation counter once per frame. Hoisting it alone changed timing
by <1 %, but it should still be cached — it is pure waste inside a 120 Hz paint path.

## Fix that works

Caching the four planes at **device resolution** (2048·dpr × 540·dpr, transform scaled) and blitting
at 1:1 restores ~4 420 ms — parity with v1.0 — but allocates **202.5 MB** of canvas memory for twelve
planes at DPR2 versus the current 50.6 MB. On a 390 px phone with DPR3 that is worse. Not acceptable
as-is; the pixel budget needs a real design decision, not a one-line switch.

## Options for the fix

1. **Two-blit composite**: keep four authored planes but pre-composite sky+far once at cache time and
   blit two planes per frame. Keeps the art, halves fill rate. Cheapest honest win.
2. **Narrow the planes** to ~1 100–1 600 px at DPR1 and accept mild scaling. Memory drops (39.6 MB at
   1 600) but the fix alone did not restore parity.
3. **Device-resolution planes with a memory cap**: cache at `min(dpr, 1.5)` and cap total plane bytes
   (e.g. 96 MB), falling back to lower resolution. Best quality/perf, needs the cap to be real.
4. **Accept it.** v1.1 is roughly half the v1.0 frame rate in software rendering. On real GPU-backed
   browsers the difference may be far smaller, but that has not been measured here and must not be
   claimed.

Recommendation: option 1 plus the hoisted `matchMedia`, then re-measure; only then consider option 3.

## Limits of this measurement

Headless Chromium with software rasterization (`--use-angle=swiftshader-webgl`, no GPU), one host,
one DPR per viewport. It is a relative regression measurement, not an absolute frame-rate claim on
Abel's machine or on real phones. No physical-device performance certifying.

`avgDrawMs` in the probe reads 0 because the pre-bootstrap `MCRenderer` property shim only wraps the
export when the module assigns it; the wall-clock tick delta is the reliable number here.
